# 2026-07-23 Kafka 단일 브로커 구축 기록

## 한 줄 요약
> 비용 절감 운영을 위해 MSK나 Cloud Map 없이 ECS EC2 Capacity Provider 기반 단일 Kafka broker를 `bridge` 네트워크 모드로 배포했고, App에서 `watching-session-changed-event` Kafka 발행까지 확인했다.

## 배경
같이보기 시청 세션 변경 이벤트를 여러 App task에 전파하기 위해 Kafka를 도입했다.

현재 코드에서 Kafka를 사용하는 기능은 시청 세션 변경 이벤트다.

```text
WatchingSessionChangedEvent
→ Kafka topic: watching-session-changed-event
→ KafkaWatchingEventBroadcastListener
→ WatchingEventBroadcastProcessor
→ WebSocket 브로드캐스트
```

관련 코드:

```text
src/main/java/com/team6/moduply/watching/event/WatchingSessionChangedEvent.java
src/main/java/com/team6/moduply/common/kafka/KafkaProduceRequiredEventListener.java
src/main/java/com/team6/moduply/watching/listener/KafkaWatchingEventBroadcastListener.java
src/main/java/com/team6/moduply/common/config/KafkaConfig.java
```

## 최종 구조

```text
ECS Cluster: moduply-prod2-cluster
└─ moduply-kafka-service
   └─ moduply-kafka-cp
      └─ moduply-kafka-asg
         └─ Kafka EC2: t3.medium
            └─ Kafka task: bridge mode, host port 9092
```

App은 Kafka EC2 private IP와 host port 9092로 접속한다.

```text
SPRING_KAFKA_BOOTSTRAP_SERVERS=<Kafka EC2 private IP>:9092
MODUPLY_EVENT_TYPE=kafka
```

## 왜 bridge로 갔는가
처음에는 Kafka/Redis 같은 내부 서비스는 `awsvpc`가 보안그룹과 task IP 관점에서 더 깔끔하다고 판단했다.

하지만 Cloud Map 또는 Route 53 Private Hosted Zone을 아직 만들지 않았고, DNS를 만들면 비용과 설정이 추가된다. `awsvpc`에서 task private IP를 직접 쓰면 ECS service가 새 task로 교체될 때 task ENI private IP가 바뀔 수 있다.

그래서 이번 비용 절감용 구성에서는 다음 트레이드오프를 감수했다.

```text
선택:
- Kafka task network mode: bridge
- host port: 9092
- App은 Kafka EC2 private IP로 접속

장점:
- Cloud Map 없이 빠르게 구성 가능
- task만 재시작되면 EC2 private IP와 host port 9092는 유지됨

단점:
- ASG instance refresh 또는 EC2 교체 시 private IP가 바뀔 수 있음
- 그때 KAFKA_ADVERTISED_LISTENERS와 SPRING_KAFKA_BOOTSTRAP_SERVERS를 수동 갱신해야 함
```

## Task Definition

처음에는 문서에 남아 있던 `docker.io/bitnami/kafka:3.7`를 사용했지만, 실제 ECS agent 로그에서 이미지 manifest를 찾지 못해 pull에 실패했다.

```text
manifest for bitnami/kafka:3.7 not found: manifest unknown
No such image: bitnami/kafka:3.7
```

로컬 `docker-compose-db.yml`에서 이미 검증한 Confluent 이미지를 사용하도록 변경했다.

```text
Image:
confluentinc/cp-kafka:7.5.3

Network mode:
bridge

Port mapping:
container port 9092
host port 9092
protocol TCP
```

리소스는 `t3.medium` 한 대를 기준으로 OS/ECS agent 여유를 남겼다.

```text
Task size
- vCPU: 1
- Memory: 3 GB

Container resource allocation
- CPU: 1 vCPU
- Memory soft limit: 2 GB
- Memory hard limit: 3 GB
```

Kafka JVM heap:

```text
KAFKA_HEAP_OPTS=-Xms1g -Xmx1g
```

## Kafka 환경변수

단일 broker KRaft 모드 기준.

```text
KAFKA_BROKER_ID=1
KAFKA_NODE_ID=1
KAFKA_PROCESS_ROLES=broker,controller
KAFKA_CONTROLLER_QUORUM_VOTERS=1@localhost:9093
KAFKA_LISTENERS=PLAINTEXT://:9092,CONTROLLER://:9093
KAFKA_ADVERTISED_LISTENERS=PLAINTEXT://<Kafka EC2 private IP>:9092
KAFKA_LISTENER_SECURITY_PROTOCOL_MAP=PLAINTEXT:PLAINTEXT,CONTROLLER:PLAINTEXT
KAFKA_INTER_BROKER_LISTENER_NAME=PLAINTEXT
KAFKA_CONTROLLER_LISTENER_NAMES=CONTROLLER
KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR=1
KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR=1
KAFKA_TRANSACTION_STATE_LOG_MIN_ISR=1
KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS=0
KAFKA_LOG_DIRS=/tmp/kraft-combined-logs
CLUSTER_ID=MkU3OEVBNTcwNTJENDM2Qk
KAFKA_HEAP_OPTS=-Xms1g -Xmx1g
```

`KAFKA_ADVERTISED_LISTENERS`에는 `localhost`를 넣으면 안 된다. App container 입장에서 접근 가능한 Kafka EC2 private IP를 넣어야 한다.

## ASG / Capacity Provider / Service

```text
ASG: moduply-kafka-asg
- instance type: t3.medium
- min: 1
- desired: 1
- max: 1

Capacity Provider:
- moduply-kafka-cp
- moduply-prod2-cluster에 연결

ECS Service:
- moduply-kafka-service
- task definition: moduply-kafka-prod-task
- desired count: 1
- load balancer: 없음
```

Launch Template 버전이 잘못 연결되면 ASG의 Launch Template version을 수정하고 instance refresh 또는 기존 인스턴스 terminate로 새 인스턴스를 띄운다. 단순 reboot은 새 Launch Template 설정을 적용하지 않는다.

## 보안그룹

Kafka는 외부에 공개하지 않는다.

```text
moduply-kafka-sg inbound
- TCP 9092 from moduply-app-sg

moduply-kafka-sg outbound
- 이미지 pull과 AWS 통신을 위해 outbound 허용
```

Docker Hub 이미지를 pull하려면 Kafka EC2가 외부로 나갈 수 있어야 한다. ECS container instance가 cluster에 붙었다고 해서 Docker Hub pull까지 보장되는 것은 아니다.

## 검증

Kafka broker 기동 로그:

```text
Awaiting socket connections on 0.0.0.0:9092.
Transition from STARTING to STARTED
Kafka Server started
```

App 로그에서 Kafka 발행 성공을 확인했다.

```text
ModuplyAsyncEvent 수신 하여 Kafka 발행
[Kafka] 이벤트 발행 성공: Topic: watching-session-changed-event, Partition: ..., Offset: ...
```

확인된 범위:

```text
App → Kafka broker publish 성공
Topic: watching-session-changed-event
```

추가로 더 확실히 보려면 consumer 수신 로그를 추가한다.

```java
@KafkaListener(topics = KafkaConfig.WATCHING_SESSION_CHANGED_TOPIC)
public void onKafkaEvent(WatchingSessionChangedEvent event) {
  log.info("[Kafka] watching-session 이벤트 수신: contentId={}, type={}, watcherCount={}",
      event.watchingSession().getContentId(), event.type(), event.watcherCount());
  processor.on(event);
}
```

## 남은 개선

- Cloud Map을 쓰지 않으므로 Kafka EC2 교체 시 private IP 기반 설정을 수동 갱신해야 한다.
- Redis도 같은 내부 주소 문제를 가지고 있으므로 나중에 `redis.moduply.local`, `kafka.moduply.local` 같은 내부 DNS 전환을 검토한다.
- 현재 Kafka 발행 실패는 로그만 남기는 best-effort 구조다. 영속성이 필요한 이벤트로 확장하면 Outbox 패턴을 도입해야 한다.
- 단일 broker라 장애 시 Kafka 전체가 멈춘다. 실무형 전환 시 3 broker 또는 MSK를 검토한다.
