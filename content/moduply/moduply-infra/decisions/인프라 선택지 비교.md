# 인프라 선택지 비교

## ECS Cluster와 ASG

클러스터는 역할별로 나누지 않고 하나만 둔다.

```text
ECS Cluster: moduply-cluster
```

역할 분리는 ASG, Capacity Provider, ECS Service로 한다.

```text
app-asg / app-cp / app-service
redis-asg / redis-cp / redis-service
kafka-asg / kafka-cp / kafka-service
```

클러스터를 여러 개로 나누면 IAM, CloudWatch, 배포 흐름, 네트워크 설정이 불필요하게 복잡해진다.

## Nginx와 ALB

| 항목 | Nginx 직접 운영 | ALB + ACM |
|---|---|---|
| HTTPS 인증서 | Let's Encrypt 직접 관리 | ACM 인증서 자동 갱신 |
| 장애 지점 | Nginx EC2가 단일 장애점 가능 | ALB 관리형 고가용성 |
| 헬스체크 | 직접 구성 | target group health check |
| 분산 라우팅 | upstream 직접 관리 | target group 자동 분산 |
| WebSocket | 설정 가능 | WebSocket upgrade 지원 |
| 비용 | 낮음 | 월 고정 비용 발생 |

분산 구조에서는 ALB + ACM을 사용한다. Spring App 2~3대에 트래픽을 분산하고, `/api/**`, `/ws`, `/api/sse` path 기반 라우팅을 하기 위해서다.

## EC2 Redis와 ElastiCache

| 항목 | EC2 Redis 단일 노드 | ElastiCache Redis |
|---|---|---|
| 비용 | 낮음 | 높음 |
| 장애 대응 | 직접 복구 | replica + automatic failover |
| 백업 | 직접 설정 | snapshot/backup |
| 모니터링 | 직접 구성 | CloudWatch 지표 |
| 운영 난이도 | 높음 | 낮음 |

현재 프로젝트는 포트폴리오/부하테스트 목적이므로 EC2 Redis 단일 노드로 시작한다. 실제 운영 서비스로 전환하면 ElastiCache Redis primary + replica를 검토한다.

## Kafka 단일 broker와 3 broker

| 항목 | Kafka 단일 broker | Kafka 3 broker |
|---|---|---|
| 비용 | 낮음 | 높음 |
| 구성 난이도 | 낮음 | 높음 |
| 장애 대응 | broker 장애 시 전체 장애 | broker 1대 장애에도 일부 지속 가능 |
| 데이터 복제 | 없음 | replication factor 3 |
| 목적 | 포트폴리오/부하테스트 | 실무형 운영 |

현재는 Kafka 메시징 흐름과 병목 관측이 목적이므로 단일 broker로 시작한다. 실제 운영형 전환 시 3 broker 또는 MSK/Confluent를 검토한다.

## API와 Realtime 서버 분리

현재 코드에서는 API와 Realtime 클래스가 서로 의존하므로 profile로 Bean을 바로 끄면 안 된다.

초기 단계:

```text
같은 Spring Boot 앱을 여러 서버에 띄움
ALB path routing으로 트래픽만 분리
```

```text
/api/**  → api target group
/ws      → realtime target group
/api/sse → realtime target group
```

이후 단계:

```text
API → Realtime 직접 의존 제거
Redis Pub/Sub 또는 Kafka 이벤트 기반 전파
api/realtime/batch profile 분리
```

## 인증 캐시 결정

`AuthService.getAuthentication()`에 `Authentication` 자체를 캐시하는 것은 비추천한다.

이유:

```text
Authentication은 권한, 잠금 상태, 비밀번호, 프로필 URL을 담는 보안 스냅샷
Caffeine은 서버별 로컬 캐시라 다중 Spring 서버에서 eviction 전파 안 됨
Redis 캐시를 쓰더라도 Authentication 객체 직접 저장은 직렬화/보안 리스크가 큼
권한 변경, 잠금 변경, 비밀번호 변경, 프로필 변경, 탈퇴까지 eviction 대상이 늘어남
```

성능 병목이 확인되면 `Authentication`이 아니라 최소 정보 DTO를 Redis에 짧은 TTL로 캐시한다.

```text
UserAuthSnapshot
- userId
- email
- role
- locked
```

요청마다 새 `UsernamePasswordAuthenticationToken`을 만든다.
