# 퍼블릭 인터넷 노출로 인한 자동 스캐너 봇 로그 점령

## 한 줄 요약
> ALB와 도메인이 공개 인터넷에 노출되면서 자동 스캐너 봇이 WordPress, PHP, Docker API, GeoServer 등 취약점 탐색 경로를 계속 요청했고, 이 요청들이 Spring App까지 전달되어 인증 실패/정적 리소스 오류 로그를 점령했다.

## 증상

운영 로그에 실제 사용자 요청과 무관한 경로가 반복적으로 찍혔다.

```text
GET /wp-login.php
GET /wordpress/
GET /.env
GET /containers/json
GET /vendor/phpunit/phpunit/src/Util/PHP/eval-stdin.php
GET /geoserver/web/
GET /index.php
GET /SDK/webLanguage
GET /remote/logincheck
```

대표 로그 형태:

```text
ModuPlyAuthenticationEntryPoint - 인증 실패: uri=/wp-login.php, code=auth09
ModuPlyAccessDeniedHandler - 인가 실패: uri=/, code=auth04, exception=MissingCsrfTokenException
GlobalExceptionHandler - No static resource assets/js/message.js
DefaultSockJsService - Invalid SockJS path ...
```

## 원인

서비스 도메인 또는 ALB DNS가 퍼블릭 인터넷에 공개되어 있으면 자동화된 스캐너가 무작위로 접근한다.

```text
외부 스캐너 봇
→ 운영 도메인 또는 ALB DNS
→ ALB
→ Spring App
→ 존재하지 않는 취약점 탐색 경로 요청
```

이 요청들은 Moduply의 정상 기능 경로가 아니다. WordPress, Laravel, PHP, Docker API, GeoServer 같은 흔한 취약점을 찾기 위한 자동 탐색이다.

Spring App 입장에서는 다음처럼 처리된다.

```text
/wp-login.php
→ 인증이 필요한 알 수 없는 경로
→ 토큰 없음
→ AuthenticationEntryPoint
→ auth09 WARN 로그
```

```text
/assets/js/message.js
→ /assets/** permitAll
→ 정적 리소스 탐색
→ 실제 파일 없음
→ NoResourceFoundException
→ ERROR 로그
```

따라서 이 현상은 WebSocket 인증 문제나 배치 수집 문제라기보다, 공개 서버가 받는 일반적인 인터넷 스캔 트래픽 문제다.

## 판단

현재 로그만 보면 공격 시도가 차단되지 않은 것이 아니라, Spring Security와 CSRF가 정상적으로 막고 있다.

```text
auth09
→ 인증 토큰 없음
→ 미인증 요청 차단

auth04 + MissingCsrfTokenException
→ CSRF 토큰 없는 POST 요청 차단

NoResourceFoundException
→ 존재하지 않는 정적 리소스 요청
```

문제는 차단 여부보다 운영 로그가 스캐너 요청으로 오염된다는 점이다. 이 상태에서는 실제 배치 실패, 배포 실패, API 장애 로그를 찾기 어려워진다.

## 해결 방향

코드에서 로그 레벨을 낮추는 방법도 가능하지만, 우선은 ALB에서 명백한 스캔 경로를 Spring App으로 보내지 않도록 차단한다.

```text
스캐너 요청
→ ALB
→ Listener Rule path match
→ Fixed response 404
→ Spring App 도달 안 함
→ App 로그에 남지 않음
```

## ALB Listener Rule 설정

대상 리스너:

```text
ALB
→ HTTPS 443 listener
→ Manage rules
```

80 리스너가 443으로 redirect만 한다면 443 리스너에 우선 적용한다.

### Rule 10 - PHP / WordPress 계열 차단

조건:

```text
Path
/*.php
/wp-*
/wordpress/*
/old/*
```

작업:

```text
Routing action: Fixed response
Status code: 404
Content-Type: text/plain
Response body: Not Found
```

### Rule 20 - PHPUnit / vendor 계열 차단

조건:

```text
Path
/vendor/*
/phpunit/*
/lib/phpunit/*
/laravel/*
/www/vendor/*
```

작업:

```text
Fixed response 404
Content-Type: text/plain
Response body: Not Found
```

### Rule 30 - 기타 스캐너 경로 차단

조건:

```text
Path
/.env
/containers/*
/geoserver/*
/SDK/*
/remote/*
/lang/legacy/*
/migadmin/*
/developmentserver/*
```

작업:

```text
Fixed response 404
Content-Type: text/plain
Response body: Not Found
```

## 우선순위

ALB 리스너 규칙은 숫자가 낮을수록 먼저 평가된다.

```text
10: PHP / WordPress 차단
20: PHPUnit / vendor 차단
30: 기타 스캐너 경로 차단
100 또는 Default: moduply-app-instance-tg로 forward
```

차단 규칙이 App Target Group forward 규칙보다 앞에 있어야 한다.

## 기대 효과

ALB 규칙에 매칭되는 요청은 Spring App까지 도달하지 않는다.

```text
막히는 것:
- /wp-login.php
- /.env
- /vendor/phpunit/...
- /containers/json
- /geoserver/web/

남을 수 있는 것:
- 아직 규칙에 추가하지 않은 새로운 스캔 경로
- 정상 사용자 요청의 인증 실패
- 실제 API 장애 로그
```

따라서 ALB 규칙만으로 모든 봇 요청을 완전히 없앨 수는 없지만, 반복적으로 로그를 점령하던 대표 경로는 크게 줄일 수 있다.

## 보안그룹 체크

ALB에서 차단해도 App EC2가 직접 인터넷에 열려 있으면 우회 접근이 가능하다.

App EC2 또는 ECS App 인스턴스 보안그룹은 다음을 만족해야 한다.

```text
8080 inbound
허용: ALB 보안그룹
금지: 0.0.0.0/0

22 inbound
허용: 내 IP
금지: 0.0.0.0/0
```

이 설정이 되어 있어야 ALB Listener Rule이 의미를 가진다.

## WAF와의 차이

ALB Listener Rule:

```text
장점:
- 추가 비용 없이 시작 가능
- 명확한 path 차단에 적합
- 설정이 단순함

단점:
- 등록한 경로만 차단
- IP별 요청량 제한, 관리형 보안 룰은 부족
```

AWS WAF:

```text
장점:
- Managed Rule 사용 가능
- Rate limit 가능
- SQLi, Known bad input 등 일반 공격 패턴 대응 가능

단점:
- 비용 추가
- 부트캠프/포트폴리오 상시 운영 환경에서는 부담될 수 있음
```

현재 단계에서는 비용 절감을 위해 ALB Listener Rule로 대표 스캔 경로를 먼저 차단하고, 필요하면 이후 WAF를 검토한다.

## 결론

이번 문제는 애플리케이션 인증 로직이나 WebSocket 인증 문제가 아니라, 공개 인터넷에 노출된 ALB가 자동 스캐너 봇 요청을 받고 있었던 것이다.

우선 조치는 ALB 443 리스너에 스캐너 경로 차단 규칙을 추가하여 Spring App까지 요청이 전달되지 않게 하는 것이다. 이 방식으로 운영 로그에서 반복적인 `auth09`, `auth04`, `NoResourceFoundException` 스캔 로그를 크게 줄일 수 있다.
