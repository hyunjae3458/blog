# 상시 운영 유지용 구조

## 목적
부트캠프 종료 후 취업 준비 기간 동안 포트폴리오 시연 링크를 계속 켜두기 위한 구조다. 부하테스트용 구조를 그대로 유지하면 월 비용이 크므로, 네트워크/배포 구조는 유지하되 인스턴스 수와 스펙을 낮춘다.

## 구조

```text
Internet
  ↓
ALB + ACM
  ↓
Spring App EC2 #1: t3.small
  ↓
RDS PostgreSQL: db.t4g.micro 또는 db.t4g.small
Redis + Kafka EC2: t3.small 또는 t3.medium
```

ECS 기준:

```text
ECS Cluster: moduply-prod2-cluster
├─ moduply-app-service
│  └─ desired count: 1
├─ moduply-redis-service
│  └─ desired count: 1
└─ moduply-kafka-service
   └─ desired count: 0 또는 1
```

Kafka가 상시 시연에 필요하지 않으면 Kafka EC2는 stop하거나 ASG desired를 0으로 낮춘다. 단, EC2를 stop해도 EBS 비용은 남는다.

## 2026-07-16 실제 상시 배포 기준

실제 재배포에서는 비용과 OAuth outbound 문제를 고려해 다음처럼 운영한다.

```text
Spring App
- ECS EC2 Capacity Provider 사용
- network mode: bridge
- target group: Instance 타입
- host port: 8080
- 이유: NAT Gateway 없이 Google OAuth 등 외부 API 호출 필요

Redis
- ECS EC2 Capacity Provider 사용
- network mode: awsvpc
- App은 Redis task private IP로 임시 접속

RDS
- PostgreSQL
- Spring App SG에서만 5432 허용
```

추후 실무형 구조로 올릴 때는 App을 다시 awsvpc/private subnet 구조로 전환하고 NAT Gateway 또는 VPC Endpoint를 붙이는 방향을 검토한다.

## ASG 기준

분리 유지형:

```text
moduply-app-asg
- min: 1
- desired: 1
- max: 1

moduply-redis-asg
- min: 1
- desired: 1
- max: 1

moduply-kafka-asg
- min: 0
- desired: 0 또는 1
- max: 1
```

더 절감하려면 Redis와 Kafka를 같은 EC2에 둘 수 있다.

```text
상시 운영 절감형
├─ Spring App EC2: t3.small 1대
├─ Redis + Kafka EC2: t3.small 1대
└─ RDS: db.t4g.micro
```

## 예상 비용

| 항목 | 월 예상 |
|---|---:|
| ALB + Public IPv4 | 약 $35~50 |
| Spring App `t3.small` 1대 | 약 $15~20 |
| Redis + Kafka EC2 `t3.small` 1대 | 약 $15~25 |
| RDS `db.t4g.micro` | 약 $15~30 |
| EBS / 로그 / 데이터 전송 | 약 $20~40 |
| 총합 | 약 $100~165+ |

## 장점
- 부하테스트 때 만든 ALB, target group, ECS service 구조를 유지할 수 있다.
- 포트폴리오 링크를 계속 열어둘 수 있다.
- 부하테스트용 스펙을 계속 유지하는 것보다 비용을 크게 줄일 수 있다.
- "검증 기간에는 확장 스펙, 상시 운영 기간에는 축소 스펙"이라는 운영 전략을 설명할 수 있다.

## 단점
- Spring App이 1대라 무중단 배포와 장애 대응은 약해진다.
- Redis와 Kafka를 같은 EC2에 합치면 병목 분석과 장애 격리가 어려워진다.
- RDS `db.t4g.micro`는 connection과 memory 여유가 작다.

## 상시 운영 시 조정할 설정
RDS 스펙을 낮추면 Hikari pool도 줄인다.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 5
      minimum-idle: 1
```

Spring App task 자체는 너무 낮추지 않는다. 현재 앱은 이미 `1 vCPU / 1.5 GB` 수준에서 운영 중이므로, 상시 운영 비용 절감은 task 스펙보다 desired count를 줄이는 방식이 안전하다.
