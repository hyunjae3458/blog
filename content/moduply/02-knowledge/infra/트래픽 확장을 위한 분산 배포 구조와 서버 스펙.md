# 트래픽 확장을 위한 분산 배포 구조와 서버 스펙

## 한 줄 요약
> 현재 `t3.small` 단일 ECS EC2 구조는 비용은 낮지만 장애 지점이 하나라서, 1만명 트래픽을 안전하게 받으려면 ALB 앞단 분산, Spring App 다중화, Redis/RDS 분리, WebSocket/SSE 연결 구조 분리가 필요하다.

## 배경 / 어떤 상황이었는가
현재 운영 구조는 단일 EC2 인스턴스 안에서 ECS 클러스터를 구성하고, App Service와 Redis Service를 나눠 실행하는 형태다.

```text
EC2 t3.small 1대
├─ ECS Service: Spring App + Nginx
└─ ECS Service: Redis
```

이 구조는 초기 배포와 비용 절감에는 유리하지만, 실무형 트래픽 환경에서는 다음 문제가 있다.

- EC2 한 대 장애 시 전체 서비스 장애
- Spring App, Nginx, Redis가 같은 머신 자원을 공유
- 무중단 배포와 수평 확장이 어려움
- Redis 장애가 인증, 캐시, SSE/WebSocket pub-sub 장애로 이어짐
- WebSocket/SSE 장기 연결이 일반 API 요청과 같은 서버 자원을 경쟁
- 배치 작업이 API 서버와 같은 프로세스에서 돌면 피크 시간에 부하 충돌 가능

## 분산 인프라와 MSA의 차이
이번 논의의 핵심은 MSA가 아니라 분산 인프라다.

```text
분산 인프라:
같은 Spring Boot 애플리케이션을 여러 서버에 띄워 트래픽과 장애를 분산한다.

MSA:
auth-service, content-service, playlist-service처럼 도메인별 애플리케이션과 DB를 분리한다.
```

따라서 지금 단계에서는 서비스별 프로젝트를 쪼개기보다, 먼저 다음 구조를 목표로 한다.

```text
ALB
  ├─ Spring API 서버 여러 대
  ├─ WebSocket/SSE 서버 여러 대
  └─ Batch Worker 별도 실행

Managed / Shared
  ├─ RDS PostgreSQL
  ├─ Redis 또는 ElastiCache Redis
  └─ Kafka 또는 MSK/Confluent
```

## 구조 1: 현재 최소 비용 구조

```text
Internet
  ↓
EC2 Public IP
  ↓
Nginx container
  ↓
Spring App container
  ↓
Redis container/service
```

### 서버 스펙

| 역할 | 스펙 | 비고 |
|---|---:|---|
| EC2 | `t3.small` 1대 | 2 vCPU, 2GiB |
| Spring App | 같은 EC2 내부 컨테이너 | JVM 메모리 제한 필수 |
| Nginx | 같은 ECS Task 사이드카 | 80/443 프록시 |
| Redis | 같은 EC2의 별도 ECS Service | App과 생명주기만 분리 |
| DB | RDS 또는 외부 PostgreSQL | 작은 스펙이면 커넥션 관리 중요 |

### 예상 비용

| 항목 | 월 예상 |
|---|---:|
| EC2 `t3.small` 1대 | 약 $15~20 |
| EBS / IPv4 / 로그 등 | 약 $5~15 |
| 총합 | 약 $20~35+ |

### 한계
- 장애 격리가 거의 안 된다.
- Redis가 같은 EC2에 있어 EC2 장애 시 Redis도 같이 죽는다.
- Spring App을 늘릴 수 없어서 CPU, 메모리, 커넥션 병목을 피하기 어렵다.
- 실무형 무중단 배포 연습에는 부족하다.

## 구조 2: 비용 절충형 분산 환경

비용을 너무 올리지 않으면서 실무형 구조로 넘어가는 1차 목표다.

```text
Internet
  ↓
ALB + ACM
  ├─ Spring App EC2 #1: t3.medium
  └─ Spring App EC2 #2: t3.medium
      ↓
RDS PostgreSQL: db.t4g.medium
Redis: cache.t4g.small 또는 EC2 Redis
Kafka: 선택 사항, 초기에는 단일 EC2 또는 미도입
```

### 서버 스펙

| 역할 | 권장 스펙 | 이유 |
|---|---:|---|
| ALB | 1개 | HTTPS 종료, 헬스체크, target group 분산 |
| ACM | Public certificate | ALB 연동 시 인증서 발급/갱신 부담 제거 |
| Spring App | `t3.medium` 2대 | 2 vCPU, 4GiB. 현재 `t3.small`보다 JVM 여유 확보 |
| Redis | `cache.t4g.small` 또는 EC2 `t3.small` | 비용이 빡빡하면 EC2 Redis로 시작 가능 |
| RDS | `db.t4g.medium` | 초기 운영/QA용. 2 vCPU, 4GiB |
| Kafka | 단일 EC2 또는 보류 | 실무 안정성을 위해서는 최소 3 broker가 필요해서 비용 부담 큼 |

### 예상 비용

| 항목                        |        월 예상 |
| ------------------------- | ----------: |
| ALB                       |    약 $25~40 |
| ALB Public IPv4           |      약 $7~8 |
| Spring App `t3.medium` 2대 |    약 $60~80 |
| RDS `db.t4g.medium`       |    약 $45~80 |
| Redis `cache.t4g.small`   |    약 $20~40 |
| EBS / CloudWatch / 데이터 전송 |    약 $20~50 |
| 총합                        | 약 $180~300+ |

### 이 구조에서 얻는 것
- Spring App 1대 장애 시 ALB가 헬스체크로 제외한다.
- rolling 배포 기반을 만들 수 있다.
- Redis/RDS를 앱 서버와 분리해 장애 전파를 줄인다.
- `t3.small` 단일 서버보다 JVM, DB, 네트워크 병목을 관측하기 쉬워진다.

### 주의할 점
- Spring App 2대가 되면 WebSocket/SSE 메시지를 메모리만으로 전달하면 안 된다.
- 서버별 Hikari connection pool 합계를 RDS가 감당할 수 있게 제한해야 한다.
- `t3`, `t4g` 계열은 burstable이라 장시간 고부하에서는 CPU credit을 확인해야 한다.

## 구조 3: 실무형 시작점

1만명 트래픽을 "안전하게 받기 위한 출발점"으로 보는 구조다. 여기서 1만명은 정확한 의미가 중요하다.

```text
1만 DAU:
비용 절충형 구성으로도 시작 가능성이 있음.

1만 동시접속:
API 서버, Realtime 서버, RDS, Redis를 분리하고 반드시 부하테스트가 필요함.
```

### 전체 구조

```text
Internet
  ↓
Route53
  ↓
ALB + ACM : 443
  ├─ /api/**      → api target group
  ├─ /ws          → realtime target group
  └─ /api/sse     → realtime target group

ECS / EC2
  ├─ Spring API #1
  ├─ Spring API #2
  ├─ Realtime #1
  ├─ Realtime #2
  └─ Batch Worker #1

Managed / Shared
  ├─ RDS PostgreSQL Multi-AZ
  ├─ ElastiCache Redis primary + replica
  └─ Kafka 3 broker 또는 MSK/Confluent
```

### 서버 스펙

| 역할 | 권장 스펙 | 비고 |
|---|---:|---|
| Spring API | `t3.large` 2대 | 2 vCPU, 8GiB. REST API 처리 |
| Realtime | `t3.large` 2대 | WebSocket/SSE 연결 유지 전용 |
| Batch Worker | `t3.medium` 1대 | API 서버와 배치 부하 분리 |
| RDS PostgreSQL | `db.m7g.large` Multi-AZ | 2 vCPU, 8GiB. burstable 의존도 낮춤 |
| Redis | `cache.t4g.medium` primary + replica | pub-sub, 캐시, 토큰 상태 저장 |
| Kafka | broker 3대, 각 `t3.medium` 이상 | replication factor를 고려하면 3 broker부터 의미 있음 |
| Storage | gp3 100~200GiB부터 | RDS와 Kafka 디스크는 지표 보고 증설 |

### 예상 비용

| 항목 | 월 예상 |
|---|---:|
| ALB + IPv4 | 약 $35~50 |
| Spring API `t3.large` 2대 | 약 $120~180 |
| Realtime `t3.large` 2대 | 약 $120~180 |
| Batch Worker `t3.medium` 1대 | 약 $30~40 |
| RDS `db.m7g.large` Multi-AZ | 약 $250~450+ |
| ElastiCache `cache.t4g.medium` 2노드 | 약 $100~180 |
| Kafka EC2 3대 + EBS | 약 $150~300+ |
| 로그 / 데이터 전송 / 스냅샷 | 약 $50~150+ |
| 총합 | 약 $850~1,500+ |

### 이 구조에서 얻는 것
- API 요청과 장기 연결 부하를 분리한다.
- Batch가 API 응답 시간을 밀어내지 않는다.
- Redis와 RDS가 앱 서버 장애와 분리된다.
- ALB target group별 헬스체크와 점진 배포가 가능하다.
- WebSocket/SSE는 Realtime 서버만 스케일아웃하면 된다.

## WebSocket/SSE 전용 서버는 어떻게 연결하는가
전용 서버를 만든다는 말은 처음부터 별도 프로젝트로 쪼갠다는 뜻이 아니다. 같은 Spring Boot jar를 profile이나 실행 옵션으로 나눠 띄우는 방식으로 시작할 수 있다.

```text
spring-api profile
- REST API
- 로그인, 콘텐츠, 플레이리스트, 리뷰
- /api/**

spring-realtime profile
- WebSocket
- SSE
- /ws
- /api/sse

spring-batch profile
- Spring Batch Job
- API 요청 처리 안 함
```

외부 포트를 여러 개 열지 않는다. 외부에는 ALB의 443만 열고, path 기반 라우팅으로 target group을 나눈다.

```text
Client
  ↓ HTTPS/WSS 443
ALB
  ├─ /api/**    → api-tg       → api-server:8080
  ├─ /ws        → realtime-tg  → realtime-server:8080
  └─ /api/sse   → realtime-tg  → realtime-server:8080
```

클라이언트 주소는 다음처럼 유지할 수 있다.

```javascript
const socket = new WebSocket("wss://api.example.com/ws");
const eventSource = new EventSource("https://api.example.com/api/sse");
```

보안 그룹은 다음처럼 둔다.

```text
ALB
- inbound: 80, 443 from internet

Spring API / Realtime EC2
- inbound: 8080 only from ALB security group

RDS / Redis
- inbound: only from Spring server security group
```

## Realtime 서버 다중화 시 메시지 전달 문제
Realtime 서버가 2대 이상이면 사용자가 어느 서버에 붙을지 알 수 없다.

```text
user A → realtime-1
user B → realtime-2
```

따라서 알림, DM, 채팅 브로드캐스트는 특정 서버 메모리에만 저장하면 안 된다.

```text
API 서버에서 이벤트 발생
  ↓
Redis Pub/Sub 또는 Kafka
  ↓
모든 Realtime 서버가 구독
  ↓
각 Realtime 서버가 자신에게 연결된 사용자에게만 전송
```

예시:

```text
PlaylistSubscribedEvent 발생
  ↓
notification/realtime 쪽에서 이벤트 소비
  ↓
receiverId가 현재 서버에 연결되어 있으면 SSE name: notifications 전송
```

## RDS sizing에서 특히 조심할 것
Spring App을 여러 대 띄우면 DB connection도 같이 늘어난다.

```text
Spring App 4대
각 Hikari maximumPoolSize = 20
총 DB connection = 80
```

여기에 Batch, Admin, Migration, Monitoring 커넥션까지 붙는다. 따라서 초기에는 각 서버의 pool size를 작게 잡고, RDS 지표를 보면서 늘리는 게 맞다.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10
      minimum-idle: 2
```

필요하면 RDS Proxy나 PgBouncer도 검토한다.

## 부하테스트로 확인해야 할 지표
스펙은 감으로 확정하면 안 된다. `k6`나 JMeter로 다음 지표를 확인해야 한다.

```text
API p95 latency < 300~500ms
Spring CPU < 60~70%
JVM heap 사용률 < 70%
RDS CPU < 60%
RDS connection 여유 있음
Redis memory eviction 없음
Kafka consumer lag 안정적
WebSocket/SSE 연결 유지 안정적
ALB 5xx, target 5xx 증가 없음
```

## 단계별 추천

1. 현재 구조에서 바로 MSA로 가지 않는다.
2. 먼저 ALB + ACM을 도입하고 Spring App을 2대 이상으로 늘린다.
3. Redis와 RDS를 앱 서버에서 분리한다.
4. WebSocket/SSE 다중 인스턴스 문제를 Redis Pub/Sub 또는 Kafka로 해결한다.
5. Batch Worker를 API 서버와 분리한다.
6. 부하테스트 결과를 보고 API/Realtime/RDS/Kafka 스펙을 조정한다.
