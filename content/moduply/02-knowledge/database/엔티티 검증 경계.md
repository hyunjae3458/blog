# 엔티티 검증 경계

## 문제
`User`, `SocialAccount` 같은 JPA 엔티티를 만들 때 필수값 검증을 어디서 해야 하는지 헷갈릴 수 있다.

서비스 단에서 `null`, 빈 문자열, 비즈니스 예외 처리를 모두 하면 충분해 보이지만, 코드 리뷰에서는 엔티티 생성자에서도 최소한의 불변식 검증이 필요하다는 피드백이 나왔다.

## 원인
서비스 검증은 중요하지만, 엔티티가 항상 특정 서비스 메서드를 통해서만 생성된다는 보장이 없다.

엔티티 생성 경로는 시간이 지나면서 늘어난다.

- 회원가입 서비스
- OAuth 로그인 서비스
- 관리자 계정 생성 기능
- 배치 코드
- 테스트 Fixture
- 다른 도메인 서비스
- 리팩터링 중 새로 생기는 생성 경로

서비스 A에서 검증을 잘 해도, 나중에 서비스 B나 테스트 코드가 `new User(null, ...)`처럼 잘못된 객체를 만들 수 있다. 이때 엔티티 생성자에 검증이 없으면 잘못된 상태의 객체가 메모리에 존재하다가 DB 저장 시점이나 더 늦은 시점에 실패한다.

`@Column(nullable = false)`도 마지막 방어선일 뿐이다. 이 제약은 DB insert/update 시점에야 동작하므로, 도메인 객체가 생성되는 순간의 불변식을 보장하지 못한다.

## 해결
검증 책임을 한 곳에 몰지 않고 계층별로 나눈다.

### DTO / Controller
사용자 요청값의 형식을 검증한다.

- `@NotBlank`
- `@NotNull`
- `@Email`
- 요청 바디 구조 검증

예: 이메일 형식이 맞는지, 이름이 빈 문자열이 아닌지.

### Service
비즈니스 규칙과 외부 상태가 필요한 검증을 담당한다.

- 이메일 중복 여부
- 권한 부여 가능 여부
- 소셜 계정 중복 여부
- 임시 비밀번호 만료 여부
- 현재 사용자가 해당 작업을 수행할 수 있는지

예: 이미 가입된 이메일인지 확인하려면 Repository 조회가 필요하므로 서비스에서 처리한다.

### Entity
객체 자신이 성립하기 위한 최소 불변식을 검증한다.

- `role`은 `null`이면 안 됨
- `SocialAccount.user`는 `null`이면 안 됨
- `provider`는 `null`이면 안 됨
- `email`, `name`, `providerId`는 비어 있으면 안 됨

엔티티 검증은 서비스 검증을 대체하는 것이 아니라, 잘못된 객체가 만들어지는 것을 막는 마지막 방어선이다.

## `Objects.requireNonNull`을 쓰기 좋은 경우
`Objects.requireNonNull`은 `null`만 막는다. 그래서 null 여부만으로 최소 유효성을 판단할 수 있는 타입에 잘 맞는다.

```java
public SocialAccount(Provider provider, String providerId, User user) {
  this.provider = Objects.requireNonNull(provider, "provider must not be null");
  this.user = Objects.requireNonNull(user, "user must not be null");

  if (!StringUtils.hasText(providerId)) {
    throw new IllegalArgumentException("providerId must not be blank");
  }

  this.providerId = providerId;
}
```

`Role`, `Provider`, `User` 참조처럼 null만 아니면 타입 수준의 최소 조건이 성립하는 값에는 `requireNonNull`이 자연스럽다.

## 문자열에는 `requireNonNull`만으로 부족한 이유
문자열은 `null`뿐 아니라 빈 문자열과 공백 문자열도 막아야 하는 경우가 많다.

```java
Objects.requireNonNull(email); // "" 통과
Objects.requireNonNull(email); // "   " 통과
Objects.requireNonNull(email); // "not-email" 통과
```

그래서 `email`, `name`, `providerId` 같은 문자열 필드는 `requireNonNull`보다 `StringUtils.hasText` 같은 검증이 더 적합하다.

```java
public User(String email, String encodedPassword, String name, Role role) {
  if (!StringUtils.hasText(email)) {
    throw new IllegalArgumentException("email must not be blank");
  }
  if (!StringUtils.hasText(name)) {
    throw new IllegalArgumentException("name must not be blank");
  }

  this.email = email;
  this.encodedPassword = encodedPassword;
  this.name = name;
  this.role = Objects.requireNonNull(role, "role must not be null");
}
```

이메일 형식까지 엔티티에서 볼지는 팀 컨벤션에 따라 달라질 수 있다. 일반적으로는 다음처럼 나누는 편이 깔끔하다.

- `null`, blank 금지: 엔티티에서 검증 가능
- 이메일 형식 검증: DTO의 `@Email` 또는 `Email` 값 객체에서 처리
- 이메일 중복 검증: 서비스와 Repository에서 처리

## 예외 선택
엔티티 생성자에서 어떤 예외를 던질지는 팀 컨벤션에 맞춘다.

단순 생성자 인자 오류라면 `IllegalArgumentException`도 자연스럽다. 반면 프로젝트 규칙상 커스텀 예외만 사용하기로 했다면 `ModuPlyException`과 적절한 `ErrorCode`를 사용할 수 있다.

중요한 점은 DB 제약 조건까지 기다리지 않고, 잘못된 도메인 객체가 생성되는 순간 빠르게 실패하게 만드는 것이다.

## 결론
서비스 단 검증은 필수지만, 서비스 검증만으로는 충분하지 않다.

엔티티 생성자에서도 최소 불변식을 검증해야 한다. 그래야 어떤 경로로 엔티티가 생성되더라도 도메인 객체가 항상 유효한 상태를 유지한다.

정리하면 다음 기준으로 판단한다.

- enum, 엔티티 참조처럼 null만 막으면 되는 값: `Objects.requireNonNull`
- 문자열 필수값: `StringUtils.hasText`
- 요청 형식: DTO validation
- 중복, 권한, 외부 상태가 필요한 규칙: Service
- DB `nullable = false`: 마지막 안전망
