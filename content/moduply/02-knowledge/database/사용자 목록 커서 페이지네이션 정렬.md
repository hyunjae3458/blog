# 사용자 목록 커서 페이지네이션 정렬

## 한 줄 요약
> 사용자 목록 조회는 `sortBy` 기준으로 정렬하되, 같은 정렬값 안에서는 UUID `id`를 보조 커서로 사용해 페이지 경계를 안정화한다. `isLocked` 정렬은 boolean 기본 정렬에 맡기지 않고 rank 표현식으로 의미를 명시했다.

## 배경
어드민 사용자 목록 조회 API를 구현하면서 query parameter가 많아졌다.

```text
emailLike
roleEqual
isLocked
cursor
idAfter
limit
sortDirection
sortBy
```

body로 받으면 API 명세와 맞지 않으므로 `@ModelAttribute` 바인딩 객체인 `UserFindAllRequest`로 묶었다.

## 요청 객체

```java
public class UserFindAllRequest {
  private String emailLike;
  private Role roleEqual;
  private Boolean isLocked;
  private String cursor;
  private UUID idAfter;
  private Integer limit;
  private SortDirection sortDirection;
  private UserSortBy sortBy;

  @AssertTrue(message = "cursor와 idAfter는 함께 전달되어야 합니다.")
  @Schema(hidden = true)
  public boolean isCursorPairValid() {
    return (cursor == null && idAfter == null) || (cursor != null && idAfter != null);
  }
}
```

`cursor`와 `idAfter`를 같이 요구하는 이유는 같은 정렬값이 여러 개 있을 때 다음 페이지 경계를 안정적으로 자르기 위해서다.

## roleEqual, isLocked 필터 보류
`roleEqual`, `isLocked`는 API 확장용 파라미터로 열어두었지만 현재 UI에서 사용하지 않으므로 필터 조건에는 반영하지 않았다.

서비스 코드에는 이 의도를 주석으로 남겼다.

```java
// roleEqual, isLocked는 API 확장용 파라미터로 열어두었지만,
// 현재 프로토타입 UI에서 사용하지 않아 필터 조건에는 아직 반영하지 않는다.
```

## 보조 정렬로 UUID를 쓰는 이유
커서 페이지네이션에서는 정렬 기준이 같은 row가 여러 개일 수 있다.

예를 들어 이름이 모두 `same`인 사용자가 세 명이면 `name`만으로는 다음 페이지 경계를 정확히 잡기 어렵다.

그래서 `id`를 보조 정렬로 둔다.

```java
.orderBy(dynamicOrder(orderBy, direction), user.id.asc())
```

UUID는 의미 있는 시간 순서나 생성 순서를 표현하지 않는다. 하지만 여기서는 의미 있는 정렬을 하려는 것이 아니라, 같은 primary sort 값 안에서 순서를 고정하는 tie-breaker로만 사용한다.

```java
// 같은 정렬 값 안에서 응답 순서를 고정하기 위한 보조 정렬이다.
// UUID는 의미 있는 순서를 갖지 않지만, 커서 경계의 tie-breaker로만 사용한다.
```

## isLocked 정렬
boolean 정렬은 DB마다 직관이 다를 수 있고, 요구사항도 명확했다.

```text
ASCENDING: 잠금 계정 먼저
DESCENDING: 미잠금 계정 먼저
```

그래서 boolean 자체를 바로 정렬하지 않고 rank를 만들었다.

```java
private NumberExpression<Integer> lockedRank() {
  return new CaseBuilder()
      .when(user.isBlocked.isTrue()).then(0)
      .otherwise(1);
}
```

의미는 다음과 같다.

```sql
case
  when is_blocked = true then 0
  else 1
end
```

`ASCENDING`이면 `0`이 먼저 오므로 잠금 계정이 먼저 나온다. `DESCENDING`이면 `1`이 먼저 오므로 미잠금 계정이 먼저 나온다.

## default 제거
`UserSortBy` enum의 모든 값을 switch에서 명시적으로 처리하도록 `default`를 제거했다.

```java
return switch (sortBy) {
  case name -> new OrderSpecifier<>(order, user.name);
  case email -> new OrderSpecifier<>(order, user.email);
  case createdAt -> new OrderSpecifier<>(order, user.createdAt);
  case isLocked -> new OrderSpecifier<>(order, lockedRank());
  case role -> new OrderSpecifier<>(order, user.role);
};
```

이렇게 하면 enum 값이 추가됐을 때 컴파일 단계에서 누락을 발견할 수 있다.

## 검증 포인트
- `isLocked ASC`는 잠금 계정이 먼저 와야 한다.
- `isLocked DESC`는 미잠금 계정이 먼저 와야 한다.
- 같은 정렬값에서는 `id` 보조 커서로 다음 페이지가 이어져야 한다.
- `cursor`와 `idAfter`는 같이 전달되어야 한다.

## 다음에 볼 것
- `roleEqual`, `isLocked` 필터가 실제 UI에서 사용되기 시작하면 QueryDSL where 조건에 반영한다.
- UUID 보조 정렬이 UX상 의미 있는 순서를 제공하지는 않으므로, 생성 순서까지 필요해지면 `createdAt + id` 조합을 재검토한다.
