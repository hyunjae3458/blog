# 계정 잠금 상태와 토큰 블랙리스트 정책

## 결정
계정 잠금 상태 변경 API는 DB의 사용자 잠금 상태와 Redis blacklist 상태를 같은 서비스 흐름에서 동기로 맞춘다.

- 잠금 요청: `locked=true`
  - `User.updateBlocked(true)`
  - Redis에 `blacklist:locked:{email}` 저장
- 잠금 해제 요청: `locked=false`
  - `User.updateBlocked(false)`
  - Redis에서 `blacklist:locked:{email}` 삭제

## 이유
계정 잠금은 단순히 DB 상태만 바꾸면 충분하지 않다.

사용자가 이미 access token을 발급받은 상태라면 token 만료 전까지 계속 API를 호출할 수 있다. 그래서 `JwtAuthenticationFilter`에서 Redis blacklist를 조회해 이미 발급된 access token도 차단해야 한다.

반대로 잠금 해제 시 DB만 `false`로 바꾸고 Redis blacklist를 삭제하지 않으면, 사용자는 DB상 잠금 해제 상태인데도 필터에서 계속 차단된다. 그래서 잠금 해제 흐름에서 blacklist key를 삭제하는 처리가 필요하다.

초기 구현은 `@Async + @TransactionalEventListener(AFTER_COMMIT)` 이벤트 리스너로 Redis 상태를 맞췄지만, 보안 상태 작업에서는 실패를 숨기면 안 된다고 판단해 서비스 동기 처리로 변경했다.

## API 명세
- Method: `PATCH`
- Path: `/api/users/{userId}/locked`
- Request body: `UserLockUpdateRequest`

```json
{
  "locked": true
}
```

- 성공 응답: `204 No Content`
- 권한: `ADMIN`

## 구현 의도
컨트롤러와 API 문서는 기존 사용자 권한 수정 API와 같은 패턴을 따른다.

- `UserController`
  - 요청 수신
  - `UserService.updateUserLocked(userId, request)` 호출
  - `204 No Content` 반환
- `UserApi`
  - `operationId = updateUser_Locked`
  - 204, 400, 401, 403, 404, 500 문서화
- `UserService`
  - `@PreAuthorize("hasRole('ADMIN')")`
  - 사용자 조회 실패 시 `USER_NOT_FOUND_EXCEPTION`
  - 잠금 상태 변경 후 Redis blacklist 저장/삭제

## 테스트 기준
- ADMIN은 계정 잠금 상태 변경 요청 시 204를 받는다.
- USER는 403을 받는다.
- CSRF token이 없으면 403을 받는다.
- `locked=true`는 DB 상태를 잠그고 Redis blacklist key를 저장한다.
- `locked=false`는 DB 상태를 해제하고 Redis blacklist key를 삭제한다.
- Redis 저장/삭제 실패 시 서비스 요청은 실패한다.

## 남은 고민
현재는 Redis 실패를 요청 실패로 전파하도록 바꿨다.

다만 DB와 Redis가 하나의 분산 트랜잭션으로 묶인 것은 아니므로, 더 강한 운영 보장이 필요하면 다음 중 하나를 결정해야 한다.

- outbox 패턴으로 재처리 보장
- 보상 트랜잭션
- 주기적 reconciliation job
- Redis 장애 시 DB 잠금 상태를 fallback으로 재조회하는 필터 전략 추가

또한 `blacklist:locked:{email}` TTL을 access token 만료 시간과 어떻게 맞출지도 검토해야 한다. 현재는 `RedisKeyPolicy.BLACKLIST_LOCKED`에 별도 TTL을 둔 상태다.

JWT 인증 필터에서 Redis 조회 실패를 `null`로 처리하면 잠긴 사용자를 통과시킬 수 있으므로, 보안 판단용 strict 조회 메서드 분리도 검토한다.
