# 프로필 이미지 동기 업로드 처리 결정

## 배경

프로필 수정 후 우측 상단 프로필 이미지와 내 프로필 관리 화면의 이미지가 즉시 반영되지 않는 문제가 있었다.

프론트 구조상 프로필 수정 API 응답을 받은 뒤 `profileStore`와 `authStore.userDto`를 수동 갱신하면 즉시 화면이 바뀌어야 한다. 그런데 같은 흐름에서도 반영 여부가 달라졌고, 새로고침 후에는 정상 반영되는 현상이 있었다.

## 원인

기존 프로필 이미지 저장 흐름은 다음과 같았다.

```text
1. BinaryContent 메타데이터 DB 저장
2. user.profileImg를 새 BinaryContent로 교체
3. 새 BinaryContent 기준 presigned URL 생성
4. UserDto 반환
5. 트랜잭션 커밋 이후 @Async 이벤트 리스너가 실제 파일 저장소에 업로드
```

이 구조에서는 URL이 먼저 반환되고 실제 파일 저장은 나중에 끝난다.

따라서 프론트가 응답받은 `profileImageUrl`을 즉시 `<img src>`에 반영하면, 브라우저가 아직 저장되지 않은 파일을 조회할 수 있다. S3뿐 아니라 로컬 파일 저장소에서도 같은 문제가 발생할 수 있으므로, 외부 저장소 속도 문제가 아니라 비동기 저장 구조의 레이스 컨디션으로 판단했다.

## 결정

프로필 이미지는 동기 업로드로 처리한다.

```text
1. 이미지 검증
2. BinaryContent 메타데이터 저장
3. 실제 파일 저장소 업로드 완료
4. BinaryContent 상태 SUCCESS 반영
5. 기존 프로필 이미지 삭제 이벤트 발행
6. 새 profileImageUrl이 포함된 UserDto 반환
```

프로필 이미지는 사용자가 수정 직후 바로 확인하는 데이터이므로, 응답 전에 실제 파일 저장이 완료되어야 한다.

추가로 S3 업로드는 DB 트랜잭션 밖에서 수행하도록 트랜잭션 경계를 분리한다.

최종 흐름:

```text
1. 짧은 트랜잭션으로 기존 프로필 이미지 조회
2. 짧은 트랜잭션으로 새 BinaryContent 메타데이터를 PROCESSING 상태로 저장 후 커밋
3. 트랜잭션 없이 S3 업로드 수행
4. 업로드 성공 시 짧은 트랜잭션으로 BinaryContent 상태를 SUCCESS로 변경
5. 기존 프로필 이미지 삭제 이벤트 발행
6. 짧은 트랜잭션으로 User.profileImg를 새 BinaryContent로 연결
7. 새 profileImageUrl이 포함된 UserDto 반환
```

이 구조는 동기 업로드의 즉시 반영 안정성을 유지하면서, S3 네트워크 I/O 동안 DB 커넥션을 점유하지 않기 위한 결정이다.

## 범위

동기 처리 대상:

- 사용자 프로필 이미지

비동기 유지 대상:

- 콘텐츠 썸네일
- 외부 API 수집 이미지
- 배치로 저장되는 이미지

콘텐츠/배치 이미지는 대량 처리 가능성이 있고 사용자가 수정 직후 즉시 확인하는 성격이 약하므로 기존 이벤트 기반 비동기 업로드를 유지한다.

## 성능 판단

동기 업로드는 해당 요청 스레드 하나를 업로드 완료까지 점유한다.

하지만 프로필 이미지는 다음 특성이 있어 동기 처리 비용이 감당 가능하다고 판단했다.

- 자주 변경되는 데이터가 아니다.
- 한 번에 한 장만 업로드한다.
- 파일 크기 제한을 둘 수 있다.
- 수정 직후 즉시 반영되는 UX가 더 중요하다.

주의할 상황은 동시에 많은 사용자가 큰 프로필 이미지를 업로드하여 Tomcat 요청 스레드를 오래 점유하는 경우다. 현실적으로 발생 가능성은 낮지만, 방어를 위해 최대 파일 크기 제한과 업로드 timeout 설정을 검토한다.

## 방어 설정

프로필 이미지 업로드는 동기 처리하되, S3 지연이 요청 스레드와 DB 커넥션을 과도하게 점유하지 않도록 다음 방어선을 둔다.

- 서버 multipart 최대 파일 크기: 5MB
- 서버 multipart 최대 요청 크기: 6MB
- `validateImage(...)` 이미지 최대 크기: 5MB
- S3 connect timeout: 3초
- S3 socket/read timeout: 5초
- S3 connection acquisition timeout: 3초
- S3 전체 API 호출 timeout: 10초
- S3 단일 시도 timeout: 5초
- S3 최대 재시도 횟수: 1회

환경변수:

```env
SPRING_SERVLET_MULTIPART_MAX_FILE_SIZE=5MB
SPRING_SERVLET_MULTIPART_MAX_REQUEST_SIZE=6MB
AWS_S3_CONNECT_TIMEOUT_MILLIS=3000
AWS_S3_SOCKET_TIMEOUT_MILLIS=5000
AWS_S3_CONNECTION_ACQUISITION_TIMEOUT_MILLIS=3000
AWS_S3_API_CALL_TIMEOUT_MILLIS=10000
AWS_S3_API_CALL_ATTEMPT_TIMEOUT_MILLIS=5000
AWS_S3_MAX_RETRIES=1
```

이 설정의 목적은 S3 지연이 발생하더라도 요청 스레드 점유 시간이 과도하게 길어지지 않게 하는 것이다.

주의할 점:

- S3 업로드는 DB 트랜잭션 밖에서 실행한다.
- 파일 크기와 S3 대기 시간을 제한해 요청 스레드 점유 시간을 방어한다.
- Spring Retry는 제거하고 AWS SDK 내부 retry만 사용해 중첩 재시도를 방지한다.
- 업로드 실패 시 새 BinaryContent 메타데이터를 삭제하는 보상 처리를 수행한다.
- 업로드 실패 시 User.profileImg 변경과 기존 프로필 이미지 삭제 이벤트는 실행하지 않는다.

## 트랜잭션 분리 이유

프로필 이미지 수정 부하 테스트에서 1초에 50회 수준의 요청을 주면, S3 업로드 대기 때문에 DB 커넥션 풀이 고갈되는 현상이 관찰됐다.

실제 운영에서 프로필 이미지 수정이 1초에 30~50회 발생할 가능성은 낮다. 하지만 S3 지연, 네트워크 병목, 일시적 장애가 발생했을 때 DB 커넥션까지 함께 묶여 고갈되는 구조는 장애 전파 범위가 커진다.

따라서 다음 기준으로 결정했다.

- 프로필 이미지는 응답 전에 저장 완료가 보장되어야 한다.
- S3 업로드는 사용자 응답 흐름 안에서 동기 처리한다.
- 단, S3 업로드 대기 시간 동안 DB 트랜잭션과 커넥션은 잡지 않는다.
- DB 상태 변경은 짧은 트랜잭션 여러 개로 나눈다.

이 방식은 코드가 단순 동기 처리보다 조금 복잡하지만, 즉시 반영 안정성과 DB 커넥션 보호를 함께 얻는다.

## 코드 변경

- `BinaryContentService#createUserProfile(...)`
  - 기존 이벤트 기반 비동기 업로드 대신 동기 업로드 수행
  - `TransactionTemplate`으로 BinaryContent 메타데이터 저장 트랜잭션과 성공 처리 트랜잭션 분리
  - S3 업로드는 트랜잭션 밖에서 수행
  - 업로드 성공 후 `BinaryContentStatus.SUCCESS` 반영
  - 기존 프로필 이미지는 업로드 성공 후 삭제 이벤트로 후처리
  - 업로드 실패 시 새 BinaryContent 메타데이터 삭제 보상 처리
  - 5MB 초과 이미지 거절

- `UserService#updateUser(...)`
  - 프로필 이미지가 없는 일반 수정은 짧은 트랜잭션에서 처리
  - 프로필 이미지가 있는 수정은 기존 이미지 조회, S3 업로드, User.profileImg 변경 트랜잭션을 분리
  - S3 업로드 중 User 수정 트랜잭션이 열린 상태로 유지되지 않게 처리

- `BinaryContentService#createContentImage(...)`
  - 기존 비동기 업로드 유지
  - multipart 업로드 이미지는 프로필 이미지와 동일하게 5MB 초과 시 거절

- `S3Config`
  - S3 HTTP client connect/socket/connection acquisition timeout 설정
  - S3 API call timeout, attempt timeout 설정
  - 과도한 재시도 방지를 위해 retry 횟수 제한

## 테스트

관련 테스트:

```bash
./gradlew test --tests com.team6.moduply.binarycontent.service.BinaryContentServiceTest --tests com.team6.moduply.user.UserServiceTest
```

검증 내용:

- 프로필 이미지 생성 시 실제 저장소 업로드가 즉시 호출된다.
- 프로필 이미지 `BinaryContent` 상태가 `SUCCESS`가 된다.
- 기존 프로필 이미지는 삭제 이벤트로 처리된다.
- 5MB 초과 프로필 이미지는 저장소 업로드 전에 거절된다.
- 5MB 초과 콘텐츠 multipart 이미지는 저장과 이벤트 발행 전에 거절된다.
- 프로필 이미지 업로드 실패 시 `SUCCESS` 처리와 기존 이미지 삭제 이벤트를 수행하지 않는다.
- 사용자 프로필 수정 응답에는 새 `profileImageUrl`이 포함된다.
