# 1만명 트래픽 대비 분산 인프라 단계적 도입 결정

## 결정
현재 `t3.small` 단일 EC2 기반 ECS 구조에서 바로 MSA로 전환하지 않고, 먼저 **비용 절감용 분산 구조**를 만든 뒤 필요하면 **실무형 수준 구조**로 확장한다.

이번 결정의 기준은 다음과 같다.

- 부트캠프 프로젝트와 포트폴리오 목적이므로 모든 구성요소를 처음부터 관리형으로 쓰지는 않는다.
- 1만명 트래픽 부하테스트에서 병목을 관측할 수 있도록 Spring App, Redis, Kafka, RDS를 분리한다.
- 실제 운영 수준으로 전환할 때는 Redis를 ElastiCache로, Kafka를 3 broker 또는 managed Kafka로 바꿀 수 있게 접속 정보를 환경변수화한다.

## 배경 / 왜 이 결정이 필요했는가
현재 배포는 단일 EC2 안에 Spring App, Nginx, Redis를 올리는 최소 비용 구조다.

```text
EC2 t3.small 1대
├─ Spring App + Nginx
└─ Redis
```

이 구조는 비용은 낮지만 다음 한계가 있다.

- EC2 한 대 장애 시 전체 서비스가 내려간다.
- Spring App, Nginx, Redis가 같은 CPU와 메모리를 나눠 쓴다.
- Spring App을 여러 대로 늘리기 어렵다.
- Redis나 Kafka가 앱 서버와 같은 머신에 있으면 부하테스트 병목 원인을 분리하기 어렵다.
- WebSocket/SSE, 배치, API 요청이 같은 서버에서 경쟁하면 1만명 트래픽 테스트 결과를 해석하기 어렵다.

## 비용 절감용 구조

### 구조 형태
포트폴리오와 부하테스트 목적의 1차 목표 구조다. 관리형 서비스는 꼭 필요한 것만 사용하고, Redis와 Kafka는 EC2 단일 노드로 분리한다.

```text
Internet
  ↓
ALB + ACM
  ↓
Spring App EC2 #1: t3.medium
Spring App EC2 #2: t3.medium
Spring App EC2 #3: optional
  ↓
RDS PostgreSQL: db.t4g.medium
Redis EC2: t3.small 또는 t3.medium
Kafka EC2: t3.medium
```

ECS를 사용한다면 하나의 ECS Cluster 안에 여러 EC2를 붙이되, 역할별로 placement를 분리한다.

```text
ECS Cluster: moduply-cluster
├─ app capacity: Spring App EC2 2~3대
├─ redis capacity: Redis EC2 1대
└─ kafka capacity: Kafka EC2 1대
```

서비스는 다음처럼 나눈다.

```text
spring-app service
- desired count: 2~3
- ALB target group 연결

redis service
- desired count: 1
- app 서버에서만 6379 접근 허용

kafka service
- desired count: 1
- app 서버에서만 9092 접근 허용
```

RDS는 ECS Cluster 밖의 AWS 관리형 DB로 둔다.

### 비용

| 항목 | 월 예상 |
|---|---:|
| ALB + Public IPv4 | 약 $35~50 |
| Spring App `t3.medium` 2대 | 약 $60~80 |
| Spring App 3대 사용 시 추가 | 약 $30~40 |
| Redis EC2 `t3.small` | 약 $15~20 |
| Kafka EC2 `t3.medium` + gp3 EBS | 약 $40~70 |
| RDS `db.t4g.medium` | 약 $45~80 |
| EBS / 로그 / 데이터 전송 | 약 $30~70 |
| 총합 | 약 $225~370+ |

### 장점
- 현재 단일 EC2 구조보다 장애 범위가 줄어든다.
- Spring App을 2~3대로 늘려 ALB 기반 분산과 rolling 배포를 경험할 수 있다.
- Redis와 Kafka를 앱 서버에서 분리해 부하테스트 병목을 더 명확히 볼 수 있다.
- ElastiCache, MSK 같은 관리형 서비스를 모두 쓰는 것보다 비용이 낮다.

### 단점
- Redis EC2 단일 노드는 장애 시 Redis 전체 장애가 된다.
- Kafka 단일 broker는 장애 대응과 데이터 복제 관점에서 실무형 HA 구성이 아니다.
- Redis/Kafka 설치, 디스크, 재시작, 모니터링, 백업을 직접 챙겨야 한다.
- EC2 수가 늘어나므로 보안 그룹, placement, 로그 수집 구성이 복잡해진다.
- `t3` 계열은 burstable이라 장시간 고부하에서는 CPU credit을 확인해야 한다.

## 실무형 수준 구조

### 구조 형태
실제 운영과 장애 대응까지 고려한 목표 구조다. Spring App은 역할별로 나누고, Redis와 Kafka는 고가용성 구성을 사용한다.

```text
Internet
  ↓
Route53
  ↓
ALB + ACM : 443
  ├─ /api/**    → api target group
  ├─ /ws        → realtime target group
  └─ /api/sse   → realtime target group

ECS / EC2
  ├─ Spring API #1: t3.large
  ├─ Spring API #2: t3.large
  ├─ Realtime #1: t3.large
  ├─ Realtime #2: t3.large
  └─ Batch Worker #1: t3.medium

Managed / Dedicated
  ├─ RDS PostgreSQL: db.m7g.large Multi-AZ
  ├─ ElastiCache Redis: primary + replica
  └─ Kafka: broker 3대 또는 MSK/Confluent
```

API, Realtime, Batch는 처음부터 별도 프로젝트로 나눌 필요는 없다. 같은 Spring Boot jar를 profile로 나눠 실행하는 방식으로 시작할 수 있다.

```text
api profile
- REST API
- /api/**

realtime profile
- WebSocket
- SSE
- /ws
- /api/sse

batch profile
- Spring Batch Job
- 외부 API 수집
```

### 비용

| 항목                          |          월 예상 |
| --------------------------- | ------------: |
| ALB + Public IPv4           |      약 $35~50 |
| Spring API `t3.large` 2대    |    약 $120~180 |
| Realtime `t3.large` 2대      |    약 $120~180 |
| Batch Worker `t3.medium` 1대 |      약 $30~40 |
| RDS `db.m7g.large` Multi-AZ |   약 $250~450+ |
| ElastiCache Redis 2노드       |    약 $100~180 |
| Kafka EC2 3대 + EBS          |   약 $150~300+ |
| 로그 / 데이터 전송 / 스냅샷           |    약 $50~150+ |
| 총합                          | 약 $850~1,500+ |

### 장점
- API 요청, WebSocket/SSE 장기 연결, Batch 부하를 서로 분리할 수 있다.
- RDS Multi-AZ와 ElastiCache replica로 상태 저장 계층의 장애 대응력이 올라간다.
- Kafka 3 broker 구성으로 broker 장애 상황에서도 메시지 유실 가능성을 줄일 수 있다.
- 각 계층을 독립적으로 스케일링하기 쉽다.
- 실제 운영 환경에 가까운 장애 격리, 헬스체크, 배포 전략을 연습할 수 있다.

### 단점
- 비용이 크게 증가한다.
- Redis, Kafka, RDS, ALB, ECS, 보안 그룹, 로그, 모니터링까지 운영 복잡도가 커진다.
- Kafka 3 broker는 topic replication, `acks`, `min.insync.replicas`, 디스크 용량까지 같이 설계해야 한다.
- Realtime 서버가 여러 대가 되면 Redis Pub/Sub 또는 Kafka 기반으로 메시지를 모든 서버에 전달해야 한다.
- 부하테스트가 없으면 큰 스펙을 써도 병목 위치를 제대로 알 수 없다.

## 상시 운영 유지용 구조

### 구조 형태
부트캠프 종료 후 취업 준비 기간 동안 포트폴리오 시연 링크를 계속 켜두기 위한 구조다. 1만명 부하테스트 때 사용한 네트워크 구조와 배포 흐름은 유지하되, 인스턴스 수와 스펙을 낮춘다.

```text
Internet
  ↓
ALB + ACM
  ↓
Spring App EC2 #1: t3.small
  ↓
RDS PostgreSQL: db.t4g.micro 또는 db.t4g.small
Redis + Kafka EC2: t3.small 또는 t3.medium
```

ECS 구조를 유지한다면 같은 ECS Cluster 안에서 service는 유지하되 desired count와 capacity를 낮춘다.

```text
ECS Cluster: moduply-cluster
├─ spring-app service
│  └─ desired count: 1
├─ redis service
│  └─ desired count: 1
└─ kafka service
   └─ desired count: 1
```

비용을 더 줄여야 하면 Redis와 Kafka를 같은 EC2에 배치할 수 있다. 다만 이 경우 Redis와 Kafka 중 하나가 문제를 일으켜도 같은 서버 자원을 공유하므로 장애 격리는 약해진다.

```text
상시 운영 절감형
├─ Spring App EC2: t3.small 1대
├─ Redis + Kafka EC2: t3.small 1대
└─ RDS: db.t4g.micro
```

### 비용

| 항목                              |        월 예상 |
| ------------------------------- | ----------: |
| ALB + Public IPv4               |    약 $35~50 |
| Spring App `t3.small` 1대        |    약 $15~20 |
| Redis + Kafka EC2 `t3.small` 1대 |    약 $15~25 |
| RDS `db.t4g.micro`              |    약 $15~30 |
| EBS / 로그 / 데이터 전송               |    약 $20~40 |
| 총합                              | 약 $100~165+ |

ALB까지 제거하고 Nginx + 단일 EC2로 돌아가면 더 싸질 수 있지만, 그러면 분산 인프라 구조와 ALB 기반 배포 설명이 약해진다. 포트폴리오 상시 운영에서는 ALB + ACM은 유지하고 Spring/Redis/Kafka/RDS 스펙을 낮추는 쪽이 더 낫다.

### 장점
- 부하테스트 때 만든 ALB, target group, ECS service, RDS, Redis, Kafka 연결 구조를 유지할 수 있다.
- 취업 준비 기간 동안 포트폴리오 링크를 계속 열어둘 수 있다.
- 부하테스트용 스펙을 계속 유지하는 것보다 월 비용을 크게 줄일 수 있다.
- "검증 기간에는 확장 스펙, 상시 운영 기간에는 축소 스펙"이라는 운영 전략을 설명할 수 있다.

### 단점
- Spring App이 1대라서 무중단 배포와 장애 대응은 약해진다.
- Redis와 Kafka를 같은 EC2에 합치면 장애 격리와 병목 분석이 어려워진다.
- RDS `db.t4g.micro`는 connection과 memory 여유가 작다.
- Kafka를 상시로 켜둘 필요가 없는 기능만 시연한다면 Kafka EC2 비용이 낭비될 수 있다.

### 상시 운영 시 조정할 설정
RDS 스펙을 낮추면 Hikari connection pool도 줄인다.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 5
      minimum-idle: 1
```

Kafka가 필수 시연 기능이 아니라면 평소에는 Kafka EC2를 stop하고, 비동기 이벤트나 알림 시연이 필요할 때만 켜는 방식도 고려한다. 단, EC2를 stop해도 EBS 비용은 남는다.

## Nginx 대신 ALB를 쓰는 이유

현재 구조에서는 Nginx가 HTTPS 종료, reverse proxy, WebSocket proxy 역할을 한다. 하지만 다중 Spring App 구조로 가면 ALB가 더 적합하다.

| 항목 | Nginx 직접 운영 | ALB + ACM |
|---|---|---|
| HTTPS 인증서 | Let's Encrypt 발급/갱신 직접 관리 | ACM 인증서 자동 갱신 |
| 장애 지점 | Nginx EC2가 단일 장애점이 될 수 있음 | ALB 자체가 관리형 고가용성 |
| 헬스체크 | 직접 구성 필요 | target group health check 제공 |
| 분산 라우팅 | upstream 직접 관리 | target group에 자동 분산 |
| WebSocket | 설정 가능 | WebSocket upgrade 지원 |
| 배포 | 직접 reload/설정 관리 | ECS Service와 target group 연동 가능 |
| 비용 | EC2만 쓰면 저렴 | ALB 월 고정 비용 발생 |

이번 프로젝트에서는 비용이 조금 늘더라도 ALB + ACM을 쓰는 것이 낫다. 이유는 다음과 같다.

- Spring App 2~3대에 트래픽을 나누려면 로드밸런서가 필요하다.
- HTTPS 인증서를 직접 관리하지 않아도 된다.
- target health check로 죽은 앱 서버를 자동 제외할 수 있다.
- `/api/**`, `/ws`, `/api/sse` 같은 path 기반 라우팅으로 API와 Realtime 서버를 나눌 수 있다.

## EC2 Redis와 ElastiCache Redis 비교

| 항목 | EC2 Redis 단일 노드 | ElastiCache Redis |
|---|---|---|
| 비용 | 낮음 | 더 높음 |
| 설치/업그레이드 | 직접 관리 | AWS 관리 |
| 장애 대응 | 직접 재시작/복구 | replica + automatic failover 가능 |
| 백업 | 직접 설정 | snapshot/backup 기능 제공 |
| 모니터링 | 직접 exporter/로그 구성 | CloudWatch 지표 제공 |
| 보안 | SG/패치 직접 관리 | VPC/SG 기반 관리형 구성 |
| 운영 난이도 | 높음 | 낮음 |

### EC2 Redis를 선택하는 이유
- 부트캠프 프로젝트와 포트폴리오 목적에서는 비용 절감이 중요하다.
- 실제 운영 서비스가 아니므로 Redis automatic failover까지 반드시 필요하지는 않다.
- Spring App과 Redis를 분리하는 것만으로도 현재 단일 EC2 구조보다 병목 관측이 쉬워진다.

### ElastiCache로 전환해야 하는 시점
- Redis 장애가 곧 인증/세션/실시간 알림 장애로 이어지는 상황
- Redis 운영과 백업을 직접 관리하기 어려운 상황
- 실제 사용자 트래픽을 지속적으로 받는 운영 서비스로 전환하는 상황
- Redis primary 장애 시 replica 승격과 자동 장애 조치가 필요한 상황

전환을 쉽게 하려면 Redis 접속 정보는 코드에 박지 않고 환경변수로 둔다.

```yaml
spring:
  data:
    redis:
      host: ${REDIS_HOST}
      port: ${REDIS_PORT:6379}
```

## Kafka 단일 broker와 Kafka 3 broker 비교

| 항목 | Kafka 단일 broker | Kafka 3 broker |
|---|---|---|
| 비용 | 낮음 | 높음 |
| 구성 난이도 | 낮음 | 높음 |
| 장애 대응 | broker 장애 시 Kafka 전체 장애 | broker 1대 장애에도 일부 지속 가능 |
| 데이터 복제 | 없음 | replication factor 3 가능 |
| 포트폴리오/부하테스트 | 충분히 가능 | 실무형 운영 설명에 적합 |
| 운영 난이도 | 중간 | 높음 |

### Kafka 단일 broker를 선택하는 이유
- 프로젝트 목적상 Kafka의 메시징 흐름과 비동기 이벤트 처리를 보여주는 것이 우선이다.
- 3 broker를 구성하면 비용과 운영 난이도가 급격히 올라간다.
- 1만명 부하테스트에서 Kafka가 병목인지 관측하는 용도라면 단일 broker로도 시작 가능하다.

### Kafka 3 broker로 전환해야 하는 시점
- Kafka 장애가 서비스 핵심 기능 장애로 이어지는 상황
- 이벤트 유실을 줄여야 하는 운영 서비스 상황
- `replication.factor=3`, `acks=all`, `min.insync.replicas=2` 같은 실무형 설정이 필요한 상황
- broker 장애 테스트까지 포트폴리오 범위에 포함하는 상황

Spring App은 Kafka broker 주소도 환경변수로 받게 한다.

```yaml
spring:
  kafka:
    bootstrap-servers: ${KAFKA_BOOTSTRAP_SERVERS}
```

초기에는 다음처럼 단일 broker를 바라본다.

```text
KAFKA_BOOTSTRAP_SERVERS=kafka.internal:9092
```

실무형 전환 시에는 여러 broker를 넣는다.

```text
KAFKA_BOOTSTRAP_SERVERS=broker1:9092,broker2:9092,broker3:9092
```

## 최종 판단
지금 프로젝트 목적에는 비용 절감용 구조로 1만명 부하테스트를 수행하고, 부트캠프 종료 후에는 상시 운영 유지용 구조로 스펙을 낮추는 전략이 가장 적합하다.

```text
ALB + ACM
Spring App EC2 2~3대
Redis EC2 1대
Kafka EC2 1대
RDS PostgreSQL
```

이 구조는 실제 운영 수준의 고가용성은 아니지만, 현재 단일 EC2 배포보다 훨씬 분산 환경에 가깝고 1만명 부하테스트에서 병목을 관측하기 좋다.

부하테스트가 끝난 뒤에는 다음처럼 낮춘다.

```text
ALB + ACM 유지
Spring App EC2 1대
Redis + Kafka EC2 1대
RDS PostgreSQL micro/small급
```

실무형 수준으로 전환할 때는 다음 방향을 잡는다.

```text
Redis EC2 → ElastiCache Redis primary + replica
Kafka 단일 broker → Kafka 3 broker 또는 MSK
Spring App 단일 역할 → API / Realtime / Batch 역할 분리
RDS 단일 AZ → RDS Multi-AZ
```

## 재검토 시점
- 월 AWS 비용이 팀 예산을 초과하는 시점
- 부하테스트에서 Spring App CPU 또는 p95 latency가 목표치를 넘는 시점
- Redis timeout, memory eviction, connection 병목이 발생하는 시점
- Kafka consumer lag가 누적되는 시점
- WebSocket/SSE 연결 수가 API 응답 시간에 영향을 주는 시점
- 실제 사용자 트래픽을 지속적으로 받는 운영 서비스로 전환하는 시점
